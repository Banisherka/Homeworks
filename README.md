# Habit Tracker API — API-first

**Зачем этот API:** чтобы мобильное и веб-приложение работали с одним и тем же списком привычек пользователя и никто не видел чужие.

Сначала написана спецификация `api.yaml` (OpenAPI 3.0.3), потом по ней сгенерирован каркас сервиса на Python (FastAPI), потом руками дописана логика.

```
api.yaml        спека: 5 операций на 2 путях
service/        сгенерированный сервис (+ доработанные руками файлы)
README.md       этот файл
```

## 1. Спека

| Глагол | Путь | operationId | Успех | Ошибки |
|---|---|---|---|---|
| GET | `/habits` | listHabits | 200 | 400, 401 |
| POST | `/habits` | createHabit | 201 | 400, 401, 409 |
| GET | `/habits/{habitId}` | getHabit | 200 | 401, 403, 404 |
| PATCH | `/habits/{habitId}` | updateHabit | 200 | 400, 401, 403, 404 |
| DELETE | `/habits/{habitId}` | deleteHabit | 204 | 401, 403, 404 |

Решения по дизайну:

* **401 и 403 про разное.** 401: сервис не знает, кто пришёл (нет токена, просрочен, подпись неверна), в ответе есть `WWW-Authenticate: Bearer`. 403: сервис знает, кто пришёл, но привычка чужая. 404: такой привычки нет вообще. Минус 403 в том, что он подтверждает существование чужой привычки; для привычек это не секрет, а для чувствительных данных я бы отдавал 404.
* **Внутреннее наружу не едет.** В DTO `Habit` нет `ownerId`, служебного номера строки, версии записи и `deletedAt`; владельца определяет токен, а не тело запроса. Схемы `HabitCreate` и `HabitUpdate` закрыты (`additionalProperties: false`), так что подсунуть `ownerId` нельзя.
* **Успех не везде 200.** POST отвечает 201 и заголовком `Location`, DELETE отвечает 204 без тела: это то, чего ждёт клиент. Во всех остальных операциях успех 200.
* **PATCH, а не PUT.** Клиент чаще меняет одно поле (например, `archived`), а не отправляет объект целиком.
* **Единый формат ошибки** `Error {code, message, fieldErrors[]}`; стек и SQL в него не попадают.

Валидность проверена двумя инструментами: `openapi-spec-validator` и `openapi-generator-cli validate` (оба: ошибок нет).

## 3. Что поправили руками

**В спеке (после первой генерации):**

* inline-enum параметра `status` стал схемой `StatusFilter`: иначе генератор терял допустимые значения и принимал любую строку;
* inline-объект в `Error.fieldErrors` стал схемой `FieldError`: вместо безымянного `ErrorFieldErrorsInner`;
* убрал обратные кавычки и `<token>` из описаний: генератор экранировал их в `&#x60;` и `&lt;` прямо в коде.

**В сгенерированном каркасе.** Все изменённые файлы, кроме `errors.py` (его генератор не создаёт), перечислены в `.openapi-generator-ignore`, поэтому повторная генерация их не тронет:

| Файл | Что было | Что сделали |
|---|---|---|
| `security_api.py` | заглушка `...`, токен не проверялся | проверка JWT (HS256, PyJWT); 401 в формате `Error`; id пользователя кладём в `ContextVar` |
| `main.py` | маршруты на корне, ошибки в формате FastAPI | префикс `/api/v1` (как в `servers.url`); обработчики: `ApiError` → `Error`, ошибка валидации → 400 вместо 422 |
| `impl/habits_api_impl.py` | абстрактный класс без логики | хранилище в памяти, проверка владельца (403/404), 409 на дубликат, 201+`Location`, 204; запрет лишних полей |
| `errors.py` | нет | исключение `ApiError` |
| `requirements.txt` | устаревшие закрепления (`uvicorn==0.13.4`, `click==7.1.2`…) | минимальный список |
| `setup.cfg` | в `install_requires` не было PyJWT: `pip install .` и Docker-сборка падали на `import jwt` | добавили `PyJWT>=2.7` |
| `tests/` | пустые заготовки с закомментированными вызовами | 14 рабочих тестов |

Почему пришлось: генератор не передаёт токен в реализацию (владельца привычки иначе не узнать), не ставит коды 201 и 204 (всё отвечало бы 200), не переносит `additionalProperties: false` и `minProperties: 1` в модели (запрет лишних полей включён в `impl`, пустой PATCH ловим проверкой).

**Что остаётся заглушкой:** хранилище в памяти (после перезапуска пусто), `currentStreak` всегда 0 (его считали бы по отметкам выполнения, а их в этих 5 эндпоинтах нет), секрет JWT по умолчанию `dev-secret` (в реальности из переменной `JWT_SECRET`), токены выдаёт скрипт, а не сервис авторизации.

Генератор печатает два предупреждения (`Failed to get the schema name: null`, `Codegen property is null`); на результат они не повлияли: спека валидна, код импортируется, тесты проходят.

## 4. Как запустить

```bash
# спека
openapi-generator-cli validate -i api.yaml

# кодоген (повторная генерация доработанные файлы не трогает)
openapi-generator-cli generate -i api.yaml -g python-fastapi -o service \
  --additional-properties=packageName=habit_tracker

# запуск и тесты
cd service
pip install -r requirements.txt
PYTHONPATH=src pytest -q
PYTHONPATH=src uvicorn habit_tracker.main:app --port 8080

# дёрнуть руками
TOKEN=$(python scripts/make_token.py alice)
curl -i -X POST localhost:8080/api/v1/habits -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' -d '{"title":"Бегать","frequency":"WEEKLY","targetPerPeriod":3}'
curl -i localhost:8080/api/v1/habits          # без токена: 401
```

Swagger UI запущенного сервиса: http://localhost:8080/docs.

**Postman (бонус):** Import → выбрать `api.yaml` → получится коллекция из 5 запросов. Проверено конвертером Postman (`openapi-to-postmanv2`): 5 запросов, авторизация Bearer, переменные `{{baseUrl}}` и `{{bearerToken}}`. В переменную окружения кладём токен из `scripts/make_token.py`.
